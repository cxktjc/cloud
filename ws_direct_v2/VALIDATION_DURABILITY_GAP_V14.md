## 保存优化及边界

旧 `apply_changes` 对每个变更重新复制根及所有父字典；同轮多单修改相同 intents 或
tracked_orders 时重复复制。现在一次事务内，每个受影响字典只复制一次；共享的旧根保持不变，
替换父分支后再修改其子分支仍单独复制，不修改历史检查点或输入值。
owner 准备增量、writer 应用增量、恢复重放均使用该优化。

Linux 支持时，已有日志段的追加改用 `fdatasync`；缺少该接口的平台继续 `fsync`。
`fdatasync` 仍同步数据及读取所必需的元数据，包括追加后的文件长度，省去不必要的时间戳元数据同步。
语义依据：[Linux fsync/fdatasync 手册](https://man7.org/linux/man-pages/man2/fsync.2.html)、
[Python os 文档](https://docs.python.org/3/library/os.html#os.fdatasync)。
新日志段文件、检查点及目录发布仍使用原来的完整同步流程。

每笔订单继续等待正向持久化回执后发送。部分写入、同步失败、日志超限会停止 writer，
不授予新订单发送回执，不在不确定的尾部继续追加。恢复格式及 state 备份方式不变。
没有引入逐条线程、主动凑批等待或发送后才记账。

新增的保存计时覆盖：

| 分段 | 范围 |
|---|---|
| 准备 | 开始保存 → 增量解码、复制、校验打包完成 |
| 写入 | 记录准备完成 → 完整 write 返回 |
| 同步 | write 返回 → fdatasync/fsync 成功返回 |
| 回执 | 同步完成 → writer 发布已提交状态并生成回执 |

这四段组成原来的“保存”。OS 调度或 GIL 等待也可能计入相应墙钟耗时，不能把“同步”
完全解读为设备内部处理时间。原“保存后→线程”继续包含回执完成至发送 worker 续发的交接。
面板显示最近实际同步方式及四段 P95，未成交明细也保留该笔各段耗时。

## 未成交明细的价格依据

在原 WS 事件消费时保存 `trigger_symbol/source/price/exchange_time_ms`，
同轮收集的不同币候选分别记录自己的触发事件。准入时保存本币采用的报价；
委托精度处理完成后记录实际提交限价。价格诊断和计时共用原有记录/反馈，不增加独立写盘或查询。

`触发价差 = (触发价 − 实际挂单价) / 实际挂单价`，显示带符号百分比。
`准入价差` 则使用本币准入报价。两者都冻结为该次下单依据，不用之后行情补算。
按原“首次实际发送”关联规则显示，后续补挂或重新下单不覆盖该首次发送记录。

示例（示意数据）：

```text
报价与挂单: 触发=XUSDT/bid0 触发价=1.01 挂单价=1 触发价差=+1.0000% 准入价=1.005 准入价差=+0.5000%
```

低于限价显示负值。跨币触发时保留触发币及其价格，但触发价差显示“不适用（跨币触发）”，
只计算本币准入价差；缺失的旧记录显示“未记录”，不伪造为 0。

## 两核压力对照

基准为 `dc92140` 的 v13，同一台 Windows 本机，固定两核、真实本机磁盘同步、
签名假 socket；背景包含 130 个近价币，1000 条历史 intents、5000 条计时记录，
每轮同时触发 8 笔，共 3 轮持续 45 秒。20ms 批量送入背景行情，检验突发调度。
本机走 `fsync` 回退；Linux `fdatasync` 分支已验证调用及失败屏障，尚无云服务器性能实测。

```powershell
& D:\program\python.exe -B -m tests.benchmark_entry_latency_v7 --samples 8 --history 1000 --signed-socket --burst --pressure-rate 36000 --cpus 2 --near-symbols 130 --timing-history 5000 --rounds 3 --round-seconds 15 --ingress-burst-ms 20 --output var/validation_v2/v14_after.json
```

两次实际负载均约 36,001 条/秒，接收约 162 万条；过载、过载丢弃、积压过期拒绝均为 0，
无错误、重复币对、重复 CID 或漏发目标币。
