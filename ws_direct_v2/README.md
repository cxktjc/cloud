## 收行情至发送提速（2026-11-23）

signal 文件改为后台读取，行情判断不再逐条检查文件；读取停滞会暂停新挂单。撤单、查询、发单使用独立队列配额，默认线程池为新单/紧急平仓保留查询不会占用的名额。待撤旧单继续精确跟踪，快速选新单时只规划有效挂单和必要的替换保留。

最新运行标识 `20261123-entry-priority-v11`：行情队列优先处理近价候选和已有订单/持仓更新，保留同币 tick/bid0 顺序；已到达的不同币候选集中准入，满挂单的多个替换也在同一轮继续完成，不再每轮只换一单等待后续行情。精确身份与订单槽使用双槽交替 `fsync`，同轮共用一次保存，保存成功后才唤醒发送线程，不占 worker 等盘；撤单静默期和空队列不广播唤醒。完整计时继续包含保存和调度；严格逐笔 10ms 尚未全部通过，实测与恢复边界见 [VALIDATION_ENTRY_PRIORITY_V11.md](VALIDATION_ENTRY_PRIORITY_V11.md)。运行时两个 `.dispatch0/dispatch1` 文件属于实际账本，备份整个 state 目录；正常退出会导出独立 JSON，回退旧代码前必须先正常停止新版 trade。

此前运行标识 `20261121-entry-parallel-v10`：同一快照的 intents/state 并行保存，两份成功后才发送；删除外层重复复核及重复报价读取，保留 socket 就绪后的最后一次内存价差复核。反馈和面板采用不可变 JSON 交接，诊断排序移到行情锁外；积压时反馈/面板先让出时间，持续负载下最多延后 1 秒刷新，实际交易和账本保存照常执行。增加真实保存完成至 worker 续发分段。两核成批行情测试含 18k/36k 每秒及队列峰值 4,346，无过载丢弃；仍未实现全场景 10ms，快盘突发未稳定提速。525 项回归、恢复边界及完整对照见 [VALIDATION_ENTRY_PARALLEL_V10.md](VALIDATION_ENTRY_PARALLEL_V10.md)。先停止旧 trade，再拉取重启生效，signal 无需为此重启。

运行标识 `20261121-entry-durable-v9`：owner 预留精确身份和名额、提交不可变快照，独立账本线程写盘，网络 worker 收到该身份的正向持久化回执后才发送。合并等待快照以减少突发重复保存，行情线程继续消费。面板拆分登记快照、等待落盘和落盘后发送，完整延迟继续包含磁盘等待。两核离线 8 币同时触发 P95 由 51.851ms 降到 23.857ms；常规单笔存在额外交接开销，仍未实现全场景 10ms。511 项回归及同脚本对照见 [VALIDATION_ENTRY_DURABLE_V9.md](VALIDATION_ENTRY_DURABLE_V9.md)。

运行标识 `20261121-entry-pressure-v8`：增加已发送订单的排队、选单、登记持久化、worker 调度、发送前分段 P95。补上 2 核、持续行情与签名发送同时发生的压力测试，含当前负载 1/2/3/5 倍、历史峰值约 3/5 倍、多币同时触发和买一变化负载。离线测试仍存在超过 10ms 的订单，高压档出现容量保护，不能据此声称实盘目标达标。498 项回归及测试范围见 [VALIDATION_ENTRY_PRESSURE_V8.md](VALIDATION_ENTRY_PRESSURE_V8.md)。本次增加验证与定位能力；下列 v7 的低压力单笔结果不代替持续负载验收。

运行标识 `20261121-entry-latency-v7`：账户文件/SQLite 读取、面板格式化输出改为独立线程，交易 owner 保留唯一的名额与精确订单状态写入口；线程间交换脱离原状态且有时效限制的消息。维护阶段之间给新行情处理机会，回包按预算应用。关键账本编码提速，仍在新身份持久化后发送。

面板增加“触发行情→出队→选中→发送”和实际发送 P50/P95/P99/最大值、≤10ms 次数。真实签名/模拟 socket 的 40 次离线测试 P95 9.196ms、最大 12.504ms，38 次≤10ms；8 笔同时跨线的最后一笔仍有 79.385ms，尚未达到全场景 10ms。497 项回归、线程约束和实测边界见 [VALIDATION_ENTRY_V7.md](VALIDATION_ENTRY_V7.md)。更新后停止旧 trade 再重启，signal 无需为本次变更重启。

## tick / bid0 双路挂单（2026-11-20）

trade 同时订阅相同 `config/symbols.txt` 币池的 `aggTrade` 与逐币 `bookTicker`。
后者从 `/public/stream` 读取 `b`（买一价）、`B`（买一量），只使用最优一档，不维护多档深度簿。
两路独立分组、连接和重连代次，任意有效事件都进入同一状态线程触发判断。
trade 两路均按每连接最多 100 个币对分组，继续订阅完整币池；647 币时每路 7 组，最后一组 47 币。
每组连接不带 `?streams=` 的原端点后，发送一次 `SUBSCRIBE`，`params` 包含本组全部
`symbol@aggTrade` 或 `symbol@bookTicker`，每次重连重新发送。日志显示 `subscription=SUBSCRIBE`、
`SUBSCRIBE sent` 和 `SUBSCRIBE acknowledged`；确认回包不代替首笔有效行情，不刷新行情时效。
启动时先按组号逐个连接全部 depth，再逐个连接 tick；前组握手并发送订阅后等 1 秒再启动后组。
首轮连接失败也会记录错误并等待 1 秒后继续后组，该组独立按原规则重试；不把失败当作行情就绪。
该间隔只用于首次启动，已建立连接继续接收，不阻塞交易状态线程；启动中停止也会取消待启动组。
更新后重启 trade 生效，signal 无需重启；独立 ticker collector 保留原 URL 订阅行为。

- 普通单判断价取有效 tick/bid0 的较小值：`gap=(判断价-原入场限价)/原入场限价`。
  前 5 单 ≤1.85%、第 6～8 单 ≤1.65%；替换仍按任意单数 ≥0.30pp、≥5 单 ≥0.22pp 优势。

  低于限价直接满足价格准入，仍遵守信号/行情有效性、满仓、8 普通单和换单优势规则。

  撤单期间实际未结订单可短时超过 8，旧单身份和成交跟踪保留到精确终态。
  2026-11-20 修正的 `abs(gap)` 只存在于 signal 面板排名；真实发布、trade 堆排名/挑选和发送检查原本均用带符号价差。

  同时比较单币/整组 bookTicker、同组 aggTrade 与公开 SUBSCRIBE，输出底层异常链、连接 IP 和循环延迟。
  现场证据、判读限制和服务器命令见 `VALIDATION_WS_DISCONNECT_DIAGNOSTICS.md`；此工具不改变 trade 行为。
  `--heartbeat-compare` 默认按正常 DNS 对照 30s/2s 心跳；`--peer-ip IP` 可固定同一入口 IP，后端仍可能不同。
  两种方式都记录控制帧且保留自动 pong 与 TLS 验证。
  `--group 2 --limit-symbols 100` 用原 200 币分组的第 2 组前 100 币对照；诊断工具保留历史分组边界，
  不对应当前 trade 的 100 币组号，DNS 和默认 TLS 均保持原口径。
- 本地队列溢出时立即撤销受影响来源分组的旧代次、禁用其旧报价，并显式计数。
  保持 WS 读取以排空网络缓冲；队列降至低水位后，仅由新报价经 owner 确认恢复。
  溢出恢复期间丢弃的事件计入 `overload_discarded`，不拿遗漏期间的报价补做交易。
  0.5s 事件积压保护继续生效；队列默认容量仍为 8192，没有靠扩容/放宽过期要求掩盖积压。
- 短连接重试按 1/2/4/8/16/30s 退避，连接有效运行至少 30s 后才重置；
  日志附连接存续时间、收包/有效数。Python 3.11+ 接收不再为每条报文创建额外 Task，
  并每 64 帧让出执行机会，避免单组缓冲持续占用事件循环；Python 3.10 保留兼容路径。
  面板显示接收/决策速率、队列/峰值、未变买一更新数、远价快速处理数与过载丢弃数。
- 手动平仓对账：新仓保存精确入场订单的交易所成交时间，筛选后续平仓证据时不再以延迟的本地记账时间为起点。
  旧仓若已看到归零而没有匹配到 SELL，可从同一精确入场 CID/OID 的账户 BUY 成交恢复时间下界，
  再核对归零与足量外部 SELL。仍保留导入/同步后的时间屏障，不凭价格或交易所总仓位删除策略持仓。
  证据仍不足会在 trade.log 写出 `manual-flat evidence pending`、筛选起点、归零时间、匹配量/缺量。

### 接收侧比价与增量账本（v12）

运行标识 `20261123-ingress-journal-v12`。接收协程按已发布模板的 2.1% 保守边界比价；
无挂单、持仓、signal 目标、候选或同币排队/处理中事件的远价，可以在接收侧完成比较并更新估值镜像。
这些计入“接收侧远价完成”，不计过载丢弃。未知模板、近价、有效性变化、同币双源的跨线/反弹仍进入 owner。
模板或关注状态改变时重新评估已完成远价；未变买一的最新时间仍参与有效性判断。
真正的分档、替换、资金、持仓及同币防重复由统一 owner 控制，发送前最新报价检查保留。

实盘发送前保存改用有序增量日志，仅编码发生变化的分支；正回执仍在真实 `fsync` 成功后签发。
后台每累计 256 个事务生成完整检查点，日志按约 4MiB 分段，成功检查点覆盖的旧段才可清理。
检查点失败保留日志并显示错误；保留量上限 128MiB，达到上限停止新提交。
追加写入失败后该 writer 停止，须排查后重启恢复，不在不确定的尾部继续追加。

运行中的 `execution_ledger.json` 是带 epoch 的入口；当前完整账本须由本版本 `OwnershipLedger` 或维护工具读取。
**备份整个 state 目录**，包含 `execution_ledger.json.journal.*` 的检查点及日志段；不能只复制两个 JSON。
正常停止会导出完整独立 JSON，并清理本次日志。旧版双槽状态可自动读取后转换，signal 无需重启。
新日志入口使用版本保护，旧代码会拒绝读取；回退代码前先正常停止 trade，完成独立 JSON 导出。
验证条件、逐笔延迟和限制见 [VALIDATION_INGRESS_JOURNAL_V12.md](VALIDATION_INGRESS_JOURNAL_V12.md)。

仍从本目录使用原 `v9711_live.execution.runner` 启动 trade；进程内部启动两路订阅，不需要额外行情进程。
接口依据：[Binance USDⓈ-M bookTicker 文档](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/ws-streams/public#individual-symbol-book-ticker-streams)。

## 下单金额

金额基数是 **trade 自己账本的 realized_balance**，不是 signal 资金、交易所钱包余额或含浮盈权益。
新账本初始资金 15U；重启继续现有资金。signal 和 trade 各自复利、各自维护仓位，
正常启动不会导入另一方或 v1 的资金和仓位。

| trade 当前实际持仓数 | 下一笔新挂单的理论金额 |
| --- | --- |
| 0 | trade 资金 × 0.5 |
| 1 | trade 资金 × 0.3 |
| 2 | trade 资金 × 0.2 |
| ≥3 | 普通单通常停止新挂；到期前最后 3m 的预挂例外、下述补挂单均使用 0.2 档 |

这是按**当前持仓数量**选择档位，不是永久给仓位编号。部分成交计一仓；
UNKNOWN/尚未确认平掉的仓位仍计数。两仓减为一仓后新单使用 0.3，减为空仓后使用 0.5。
已有持仓不补仓、不改量。

- 持仓数量改变时，未成交的普通旧档挂单先撤单，精确终态确认后再按新档挂单；补挂单保留原数量。
- 撤单或下单回报丢失时保留原身份和占位，等待账户流/精确查询，不盲目重复下单。
- 普通单每次新的物理下单先持久化递增序号，再注册和发送；同 bar 撤后重挂和重启均不复用旧 clientOrderId。
  UNKNOWN 保留原身份和占位，不因换序号重发；换出不补回、拒单抑制和查询确认不存在后的重试上限按原计划保留。
  查询、缓存、撤单和下单回包均校验精确身份，旧 orderId 不能覆盖已确认的新 orderId。
- 持仓档位未改变时，资金浮动不会反复撤改同一笔已挂订单。下一笔新单使用最新资金。
- 8 个竞争挂单使用挂出时所见的持仓数；挂单数不当作已成交仓数。
- 最低 5U、币对 minNotional/minQty 和 stepSize 向上对齐规则继续生效。
  例如 15U 资金的三个理论档是 7.5/4.5/3U，后两档实际至少 5U。
  理论金额与实际委托金额的绝对差额超过 0.5U 时，面板才显示该单的资金档位及金额提示；差额等于 0.5U 时不显示。

**并发成交边界：**多笔已到交易所的旧档挂单可能在撤单确认前成交，真实成交全部记账。
50/30/20 不是严格的一倍总敞口限制；最低金额、并发成交和 v1 的到期前预挂例外均可能提高敞口。
精确保证每次成交恰好依次为 50/30/20，需要改变多挂单执行结构，不属于本次金额替换。

## signal 持有、trade 未持有的补挂单

trade 按 **signal 该笔持仓的原入场限价**补挂 BUY LIMIT/GTC，跨 bar 保留，
直到该 signal 持仓结束才撤掉未成交单。不套用普通挂单的价差门槛或每根 bar 到期撤单，
也不参加普通挂单的排名替换。signal 确认入场时，若已有同笔同价挂单，直接保留原订单身份。

- **最多额外 2 单**，不占普通 8 单名额，不影响普通挂单的分档计数；面板分开显示。
- trade 有 3～5 仓时也可补挂；**达到 6 仓即停止补挂，并发起撤掉已有补挂单**。
  第 6 仓成交入账后，后台发送闸门同时禁止继续发送已排队的补挂单。
- 撤单未确认、下单 UNKNOWN 都继续占用额外名额，不重复发单；重启续接原身份。
- 缺口超过 2 个时，先补 signal 入场较早的持仓，同时间按币对排序；有空位后继续补。
- 新补挂按 trade 当时实际仓数使用 50/30/20，最低 5U 和交易所精度规则生效。
  发出后固定这笔订单的价格、数量及金额档位，不随其他持仓数量或资金变化撤单重挂，重启继续保留。
  普通单转为补挂单时同样保留已挂身份和数量；部分成交后已算 trade 持仓，撤掉余单，不给已有仓位补量。
- 保留行情、账户流和精度就绪检查，以及平仓后 60 秒保护和强平/手动平仓保护。
  signal 短暂不可读或过期时不新增补挂，也不据此猜测持仓已结束。

已到交易所的订单可能在撤单确认前继续成交，真实成交全部记账；“6 仓停止补挂”
是发送和撤单规则，不能抹掉撤单竞态中已经发生的成交。成交后的到期平仓沿用该 signal
持仓的原到期时间，仍提前 1 秒开始，不从补挂成交时重新计算持仓期。

## signal 与参考回测的关系

signal 改为独立三仓模型，同一完成 bar 内按币对顺序依次使用 50/30/20，
按完成 3m 数据确认模型入场，使用上一根完成 close × (1−2.5%) 提前生成限价，K=4。
trade 用内部 WS 的实际到达顺序执行，成交及收益由精确交易所回报确认；signal 不是实际成交证明。

trade 的定时平仓在持仓最后一根 bar 结束前 **1 秒**开始，原计划到期时间保持不变。
平仓使用 SELL LIMIT/GTC `priceMatch=QUEUE`：每次确认挂出后等 **5 秒**，
未全部成交则撤单，精确确认终态、结算累计成交后，以剩余仓位重新挂 QUEUE。
**包括首单在内最多挂 12 次**；第 12 次撤单确认后，剩余数量用 MARKET 兜底。
提前全部成交即停止；明确拒绝 QUEUE 时直接进入原有 MARKET 兜底。
撤单/查询/网络延迟会增加总耗时，状态不明时继续核对原单，避免重叠平仓。
轮数和订单身份持久化，重启接着执行；旧 60 秒 QUEUE 单按原订单身份恢复到 5 秒等待。
v2 固定执行 5 秒 × 12 次，旧 `.env` 中的 `V9711_LIVE_CLOSE_LIMIT_SECONDS` 不再生效。
保留原有显式关闭开关：`V9711_LIVE_CLOSE_LIMIT_ENABLED=0` 时直接 MARKET，默认开启限价流程。
此变更只影响 trade；signal 仍按完成 bar 确认模型退出。**没有新增参考目录的 25% 止损。**
参考脚本另使用当前 bar open 生成入场价、固定 slot 权重及含持仓估值权益，
因此本版本不是该回测脚本的逐项实盘复刻，也不声称复现其收益。没有进行新策略回测或调参。

## WS 与文件路径

```text
完成 3m → signal 提前发布本 bar 全候选模板 → desired_orders_ws.json
aggTrade → trade 内存准入/持久化身份/派发 → 内存价格镜像 → 异步 latest.json → signal
```

trade 不读 `latest.json` 决定开仓，文件写出在该 tick 决策之后；保留独立网络工作通道、
8 个普通挂单分档、最多 2 个独立补挂单、撤旧再换新、价格新鲜度/重连代次保护、
账户流确认、手动/强平恢复及交易 WS 保活。
signal/trade 面板按变化刷新，最多每 3 秒一次。

运行路径由 **v2 代码所在目录**推导；旧环境变量、启动工作目录不会重定向账本。

不需要删除或修复旧账本。旧目录仅保留 trade 进程锁，避免旧 trade 与 v2 同时运行。
首次启动创建独立 15U 实盘账本；
可证明的首次空账本写入中断会自动继续。已有账本损坏、缺半份或身份不符时不会重置。

两个终端分别运行（trade 命令会提交真实订单）：

```bash
cd /opt/v9711-live/cloud/ws_direct_v2
/opt/v9711-live/cloud/.venv/bin/python -B -u -m v9711_live.run_signal
```

```bash
cd /opt/v9711-live/cloud/ws_direct_v2
/opt/v9711-live/cloud/.venv/bin/python -B -u -m v9711_live.execution.runner --enable-live --no-dry-run
```

模拟必须在两个命令后都加 `--paper`，trade 不加实盘开关。禁止模拟写入 live state。
同时只运行一个写 v2 价格镜像的 trade。systemd 模板独立命名为
`v9711-ws-v2-signal.service` / `v9711-ws-v2-trade.service`，不会覆盖 v1 的 unit 文件。
安装模板不会启动服务。

## 可选的一次性手动账本同步

正常运行不自动同步 signal 资金/仓位。如操作员明确需要一次性同步，先停止 signal/trade，
核对模型仓位与实际 Binance 持仓一致，预览后再应用。该工具只改本地记账，不执行 BUY/SELL；
不会把模型仓位变成交易所已成交订单。原执行文件保存在 `var/state/execution_backups/`。

```bash
/opt/v9711-live/cloud/.venv/bin/python -B -m scripts.sync_signal_to_trade
/opt/v9711-live/cloud/.venv/bin/python -B -m v9711_live.execution.runner --sync-signal-ledger
```

保留 v1 已有的 `--price SYMBOL=PRICE` 预览及 runner 的 `--sync-price SYMBOL=PRICE` 应用参数。
应用后退出，正常启动不再加同步参数；trade 继续独立维护资金与持仓。
历史兼容的迁移模块保留供离线维护；正常 v2 启动不调用 v1 自动接管流程。
