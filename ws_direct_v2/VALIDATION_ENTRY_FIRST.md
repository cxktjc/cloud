# v2 新单优先、反馈及日志后台写盘（2026-11-20）

基线 `8af0be6`。用户要求新发单优先，普通撤单、本地反馈和日志可以延后。未连接交易所或部署服务器，未改变信号/QV、挂单门槛、持仓/补挂容量或平仓参数。

## 原顺序与本次顺序

原来已经不等待撤单 ACK，但新单前仍可能有多次同步保存：换单预留、各笔撤单标记、序号预留、订单注册；维护末段的反馈 JSON 写盘还会阻塞随后到来的行情。日志 FileHandler 也由调用日志的线程执行文件 I/O。

本次顺序为：

1. 消费行情、应用已知回报，检查账户/信号/价格/容量，计算准入及替换。
2. 在 owner 内存中标记待撤旧单，保留精确身份，释放有效普通单名额。
3. 合并保存本笔新身份、递增序号、intent、占位和换单/待撤状态；确认保存后立即派发新单。
4. 新单进入派发路径后，再提交该计划的普通撤单。就绪新单优先级高于普通撤单；撤单仍一笔一笔执行，每笔回包后间隔 1.5s。
5. 反馈文件的 JSON 编码和写盘由独立线程执行；日志文件及日志控制台输出由队列监听线程执行。

第 3 步仍在发送前。它用于保证进程在发送后、收到回包前中断时，重启仍能准确核对该 clientOrderId，避免重复下单。没有把所有关键状态改为“发完再记”。正常注册原先的序号单独保存现已与注册合并，一次发送前屏障最多重写两份变化的账本；初始化、已有成交核对等可能另有必要落盘，不能理解成整次启动到首单只有两次写盘。落盘失败时不派发新单。

owner 回调和入场计划内的连续 save 合并，普通撤单不再先逐笔写盘卡住该计划的新单。新 entry/close 的所有实际派发入口仍检查并完成待持久化状态。账本仍只由 owner 写，不交给反馈线程。

主循环每次到维护时刻，先给已排队行情最多 32 个事件、约 2ms 检查预算的一次机会，再执行维护；不长期饿死持仓核对和平仓计时。单个事件内不可中断，故预算不是硬性 2ms 最大耗时承诺。不重排、合并或丢弃变化行情，也不抢占已在执行的网络调用。同币对串行和紧急退出通道保持原规则。

## 后台反馈及日志

反馈提交时由 owner 复制完整嵌套快照，线程只拿副本，不读取可变账本。只保留一份尚未开始写的最新反馈，正在写的文件先完成，再写最新版本；这是面板/状态反馈，不是行情或订单事件。后台保留原子替换、fsync 和失败重试。面板显示待写、最近后台写盘耗时及错误；owner 的 feedback 阶段现在主要是整理/复制/提交耗时。

单线程串行写反馈，防止旧快照晚完成覆盖新快照；关闭 trade 时等待最后快照写完，再释放进程。`--once` 和未开启后台网络的离线兼容路径仍同步反馈。反馈较旧时保留原 owner 时间戳，不用后台写盘时间冒充新状态。

日志队列保留全部日志记录；文件/控制台沿用原格式和 WS 控制台过滤规则。正常退出等待队列写完。订单关键账本没有依赖日志队列恢复。
