# 收到行情至发送提速与线程通信（2026-11-21）

运行标识：`20261121-entry-latency-v7`。目标是缩短本机收到 WS 行情至实际调用发送的时间，交易所回包/撮合不计入这段。实测接近单笔 10ms，但未达到所有场景、所有订单都低于 10ms；见下面的突发测试。

## 并发边界

| 线程/通道 | 承担的工作 | 可以修改的状态 |
| --- | --- | --- |
| 行情接收线程 | tick、bid0 校验与入队 | 各自行情缓存/连接代次，不修改执行账本 |
| 交易 owner | 判断、名额预留、精确 CID、仓位记账、派发 | 唯一执行状态写入者 |
| 新账户读取线程 | 本地账户 health、SQLite 精确订单、手动/强平证据读取 | 仅内部有界结果缓存，不接触账本、broker 或名额 |
| 原网络 workers | 接收 owner 放行的精确请求并发送 | 不修改账本；通过完成消息回 owner |
| 新面板线程 | 已脱离执行状态的面板快照、格式化和清屏输出 | 仅自身显示状态 |
| 原反馈/日志线程 | 普通反馈与日志落盘 | 不决定开仓 |

执行入口继续串行预留名额，避免两个来源同时为同币或同一空位下单。没有将多个线程直接接到可变的 `tracked`、`positions` 或 ledger 上。

## 本次修改

1. `BackgroundAccountView` 以消息方式执行只读账户查询。owner 发出精确参数请求，未完成时返回 `StreamUnavailable`，保留原订单身份，不等待 SQLite。结果按参数键隔离并复制后交还，最多 128 个键，活跃键约 25ms 刷新。结果及 health 超过 250ms 未刷新即不可消费；原账户发布 TTL 仍校验，并按经过时间递增 age，不延长账户有效期。健康首次未就绪时暂停新入场。
2. 交易所重复负查询后的最终“原单不存在”确认，必须等待一个 **开始时间晚于最后负回包** 的新账户读取。缓存 `None`、尚未完成的读取和读取异常均不释放名额；已有精确 ACK/成交优先。时间屏障使用高精度 `perf_counter_ns`，避免部分 Windows Python 的低精度单调时钟将先后事件记为同一个值。读取结果变化/屏障完成时只发送唤醒通知，owner 在下一轮立即安排对账并重新检查手动/强平证据；不额外等 250ms 维护轮询，内容相同的刷新不重复唤醒。
3. 面板格式化/JSON 比较/清屏移到独立线程。owner 交出脱离原状态的快照，普通显示允许只保留最新一份；这是显示快照的合并，不合并行情变价事件。
4. 维护在安全阶段边界让已排队行情获得处理机会，每次最多 32 条、约 1ms 预算；单条完整动作不可中断，因此不是 1ms 硬上限。恢复维护后重新读取信号，避免旧局部快照覆盖新准入/目标。
5. 每次回包应用最多 8 笔、约 1ms 预算，至少处理一笔后才检查预算；保留其余完成消息。单笔记账不可中断。退出时仍排完全部完成回调。
6. 关键 JSON 持久化由 `json.dump` 的逐片编码写入改为 `json.dumps` 后一次写入。仍保留 `flush`、`fsync` 和原子替换，新身份/物理占位仍持久化后派发，没有改为先发后记。
7. 手动平仓证据尚在后台读取时，不再把这一轮标为已查完；下一维护轮即可重试。

原有 1.5s 普通撤单节奏、逐事件变价处理、0.5s 积压保护、UNKNOWN 不盲重发、普通/补挂名额、替换门槛、signal 策略/QV 均保留。网络请求本来就由后台执行，本次着重拆出此前仍占用 owner 的账户文件/数据库读取和展示工作。

## 延迟证据

Windows 本地，800 个候选模板、1,000 条历史精确身份记录、原有 19 个网络 workers，真实临时账本与 `fsync`。基准为完整提取的提交 `52ae797`，与当前实现分别运行同一个测试脚本，未并行跑其他测试。

`--signed-socket` 使用真实 broker 线程/协程通讯、准入复核、HMAC 签名和请求序列化，连接提前预热；仅底层 socket 被替换为进程内模拟，阻断全部真实网络。结束点为模拟 `socket.send` 入口。它不包含 TLS/内核发送开销、云端负载和交易所网络 RTT，也不是撮合延迟。接收/发送外部计时使用 `perf_counter_ns`，不依赖可能粗粒度的 Windows 单调时钟。

| --- | ---: | ---: |
| 单笔依次到达 40 次：P50 | 13.364ms | 8.033ms |
| 同上：P95 | 14.382ms | 9.196ms |

当前阻塞测试中的新单在账户读取被解除前已实际调用模拟 socket。该项只有一笔受测订单，不当作分位数。另有省略真实签名/broker 的简化测试：40 次 P95 8.016ms、最大 8.100ms；不将这一简化结果当作完整发送链路。

突发测试保留了每笔登记后即发送、不等后续登记的行为。它也直接暴露剩余限制：多笔新单的选单和关键持久化仍经同一个入口，后面的订单会排队；增加后台 I/O 线程并不自动让 8 笔都在 10ms 内完成。本次未实现全场景 10ms 保证。

## 线上计时与验证

保留原“收到依据报价→选中/登记/发送”时间，另外区分触发本次判断的事件：

- `触发行情→出队`：触发事件的本机接收至进入 owner `decide`，在代次检查/行情锁校验前取点。
- `出队→选中`：校验、筛选与选单。
- `触发行情→发送`：本次触发事件至发送边界。
- `依据报价→发送`：实际选用 tick/depth 报价的年龄至发送，可能与触发事件不同。

面板显示这两种发送延迟的 P50/P95/P99/最大值及 ≤10ms 次数，最近最多 512 次登记中有发送记录的样本；ACK 时间不混入其中。维护触发的订单没有伪造一个 WS 出队时间。重启清零，启动后旧订单没有采集的数据不回填。

完整回归通过 497 项，包括账户读取阻塞/超时、后负回包读取屏障、晚到成交/ACK 优先、结果变更唤醒而不因相同刷新空转、诊断与输入隔离、后台面板阻塞、预算后继续消费完成回调、退出排空、维护让出后信号变更、并发 tick/depth 只预留一次以及原身份/容量/撤单/平仓保护。测试没有真实下单或修改生产账本。
