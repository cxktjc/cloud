# 2026-11-23：行情准入优先处理与双槽保存

运行标识：`20261123-entry-priority-v11`。仅修改 cloud 仓库 `ws_direct_v2`。
这是执行工程验证，全部订单发送到离线假 socket，没有访问交易所或修改生产账本。

## 执行路径

固定接收线程 → 有界行情队列 → 单一状态 owner 挑选和预留名额 → 不可变快照 →
后台持久化成功 → 就绪通知 → 固定网络 worker → 已预热 WS → socket 发送。

没有为每组行情临时创建线程。容量、同币身份和持仓归属由一个 owner 更新；
固定 worker 处理独立网络请求，接收线程不等待网络 ACK。发送耗时仍从原始本机
接收时间计到实际 socket 发送，包含保存、线程调度和发送前检查。

### 行情队列

原来所有币的变价共用全局 FIFO。新队列让可能产生入场、撤改或持仓处理的币优先，
可以越过无关币的远价事件。阈值仅用于保守分类，使用现有限价上方 2.1% 的范围，
不是放宽实际入场条件；真正下单仍使用原有分档和替换门槛。

同一币的 tick/bid0 共用一条顺序，较晚的触发必须先处理该币所有前序事件，
包含急跌后反弹的 A→B→A。已有候选、挂单、持仓和 signal 目标币的远价反弹也
进入优先通道，防止旧的近价排名一直占位。新 signal 模板会重新分类排队事件。
每连续 16 次优先处理后给普通 FIFO 一次机会，防止远价事件饿死。

已到达的不同币近价候选最多集中取 8 个，用一次计划统一排序、预留和发送；
不等新的行情凑批。遇到同一币第二次更新、已有候选/挂单/持仓更新、远价前序或
网络完成通知就停止收集，不跨过这些事件。每条仍执行代次和时效验证并独立计数，
每笔订单记录自己那条触发行情的时间。其他币的已接收反弹仍由最终检查阻止旧价发送。

保持原有队列容量、断线代次、新鲜度保护和过载计数；没有通过合并或删除变价来降低延迟。
超出机器处理能力仍可能触发容量保护，本修改不承诺任意速率下永不积压。

### 保存与发送交接

signal 文件的 stat/JSON 读取移到独立线程，名义每 5ms 检查一次，变更通知 owner；行情处理只取配对的内存 payload/revision。
超过 100ms 没有完成读取、文件缺失或无效时不再提供可发单输入，发送前账户/输入门也验证读取线程健康。
signal TTL、官方 bar 范围和 signal_ready 仍由 owner 与发送门检查；检测周期不是操作系统调度的硬上界。
一次性运行保留同步读取，正常 live 循环和压力脚本使用后台读取。
精度缓存的 stat/open/JSON 读取也移到 worker 共用锁外；完成后一次性发布 payload/revision。
已有 worker lane 使用共享的配对快照，不能把旧 payload 和新 revision 混在一起，文件更新后已有 lane 也会看到新精度。
准备新精度快照的文件读取阻塞时，发送线程仍可使用上次完成的快照；无效结果发布后会使预检失败。

缺省 exit_due_ms 的计划签名现在与规划器统一按 exit_due_epoch×1000 补齐，避免规范化前后身份不一致，
反复规划同一条已禁止重挂的候选。正式压力输入也补齐该字段；缺字段导致重复规划的旧压测不作为性能依据。

满挂单时，原规划器每次只返回一笔替换；即使同轮已收集多个更近的新候选，后面的候选仍要等待下一次规划。
现在只在行情线程的短候选列表内连续完成有进展的替换，最多 8 次；同轮全部新身份共用一次完整保存。
没有新增精确身份或仍存在未消费的替换保留时立即停止，避免明确拒绝或结果不明时循环重试。
每个旧单仍保留独立 CID、待撤标记和新单的 rotation_origin，撤单继续按原 1.5 秒节奏执行。
维护阶段仍只规划一次，不对全量币池执行这个重复循环。
异步快速规划也不再把已进入撤单队列的旧单反复作为候选处理；若旧单属于尚未消费的 pending_rotation，仍保留它。
所有旧单继续留在 tracked、精确账本和维护重试中。快速快照仍读取全部 tracked 的行情用于撤单距离排序，
不能为了减少规划工作把待撤单价格清空。同步/一次性旧模式保留原重试行为。

精确 intent 和实际占用的订单槽写进同一份完整快照，一次成功才签发包含对应
`(symbol, CID)` 的回执。后来的合并快照如果已不包含该身份，旧任务不能发送。
同一轮准入的多个登记先共用未就绪回执，全部预留完成后只序列化、提交一次完整
快照，再转交真实保存结果；不为一组 8 个订单重复启动多轮保存。

启动时预先建立两个固定文件 `execution_ledger.json.dispatch0/dispatch1`，以后轮流
写入未使用的一槽并执行真实 `fsync`，减少每次创建临时文件和重命名的开销。
每槽包含 epoch、递增序号、长度和 SHA-256。恢复读取当前 epoch 中最高完整序号，
中断的新写入不影响上一槽；两个槽均无效时停止，不能改读旧的导出文件继续交易。
这验证的是写入中断恢复，不是存储介质任意损坏后的完整性保证。

启用槽文件前先保存完整独立 JSON，再复用旧槽，最后发布 epoch 标记；正常退出后
再导出完整独立 JSON。运行期间标记 JSON 内的初始 state 不是最新账本，必须使用
本版 `OwnershipLedger`/启动和维护工具读取；备份应包含整个 state 目录。
`execution_intents.json` 是兼容导出，恢复以槽内配对的 intents/state 为准。
人工同步工具使用同一解析方式，并把两个槽纳入备份。

保存等待中的任务留在就绪队列，不占住网络 worker。共享一个快照的订单只登记
一次就绪通知；保存成功后只唤醒可执行任务需要的线程。撤单计划刷新、完成回调
也不再无条件广播给 19 个线程，1.5 秒撤单静默期不会为不可执行的撤单反复唤醒线程。
同币的后续操作不能越过正在等待保存的订单；其他币可以继续发送。

网络排队配额分开：普通修改请求 64、查询 64、限速入场撤单 1024，均有界；不是扩大 8 单或持仓名额。
新入场优先级高于查询，默认 19 个 worker 的远端查询最多占 11 个，给新单/紧急平仓留下 8 个 worker。
撤单仍只允许一个执行中，回包后等待 1.5 秒；其积压不能耗尽发单队列配额。已运行的查询不会被强制中断。
小于等于 8 worker 的显式旧配置保留原查询并发上限，默认 19 worker 的保留规则才适用。

普通入场 `NEW/零成交` ACK 的精确登记和保存仍立即执行，但不再为每个 ACK
额外启动一轮全量维护；成交、撤单、拒单、未知结果仍触发紧急维护，未检查完的
回调尾部也按紧急处理。账户变更通知和原周期维护继续执行。
最近 512 笔计时改用固定长度索引，不再为统计窗口扫描本进程全部历史；
历史精确记录仍可用于入场身份匹配和漏开明细。
网络唤醒后的回调同样按一个有界 owner 处理批次保存，避免每个 ACK 都重新编码
整份账本；新的 entry/close 仍会在其精确身份提交后才发送，回调失败仍保留重试。

owner 登记新订单后使用一次 `sleep(0)` 主动让出当前线程时间片，不等待磁盘或网络。
没有取消最终最新价差复核、改变 0.5 秒报价新鲜度、放宽持仓/有效普通挂单容量或缩短撤单间隔。

## 计时口径

新增真实开始保存时间，细分登记→开始保存、开始保存→回执、回执→worker、发送准备。
保存尚未完成时 worker 现在不运行，因此“登记→worker”包含保存等待；新版面板
直接显示保存等待和保存后调度，不把这段减少到零冒充完整链路提速。
明细的“落盘完成”取协调者完成时间，不再用稍晚的 worker 恢复时间代替。
完整接收→发送和原有触发/依据报价两个口径均保留，分位数不能相加。

## 验证条件

800 币，2 个逻辑 CPU 亲和性，19 个固定网络 worker，真实临时文件写入和 `fsync`，
真实 broker 事件循环、签名和 JSON 编码，到离线假 socket。账户健康、订单回报和
终端使用替身，没有 TLS、公网和实盘面板负载；本机 CPU 亲和性不能等同云端 CPU 配额。
默认 5/32 tick、27/32 未变买一，因此约 15.625% 原始行情进入决策队列。
长压测保留 5,000 笔历史计时，完整状态含约 54KB 确定性 SHA-256 十六进制填充及实际活动记录。
近价场景使用 130 个 1.7% 距离的背景币，加上更近的新机会，覆盖已有挂单的替换；背景价格可用 --changing 交替变化。
初始模板和实际 signal 一样提供完整的到期毫秒字段，不以缺字段导致的重复规划衡量吞吐。
策略 epoch 固定在一个有效 3m bar 内以隔离吞吐；本机接收、排队、保存和发送
计时使用真实高精度时钟，报价的本机时效验证仍执行。长场景使用零成交 NEW
回包和真实节奏的假撤单，没有真实持仓和平仓负载。真实换 bar、账户变化、平仓
等逻辑由回归覆盖；这些组合的实盘延迟不在本轮压测上界之内。

压力脚本新增 `--require-ms 10`，完整性/负载失败返回 1，完整性通过但延迟目标失败
返回 2；只有两个条件都通过才返回 0。10ms 检查包含背景币实际发出的订单，不仅检查预定注入的新机会。
背景订单的依据报价可能早于容量释放/替换条件成立；完整报价年龄仍保留，不删除这些慢样本。
不会用“脚本跑完”代表 10ms 验收通过。

原始记录位于忽略目录 `var/validation_v2/`。最终结果与可复现命令在本文件后续部分。

### 持续近价压力

2 个逻辑 CPU、36,000 原始行情/s、130 个近价背景币；生产压力持续 300 秒，额外约 1 秒收尾。
每 15 秒同时注入 8 个更近的新机会，1 秒后反弹，共 160 次机会；保留 5,000 笔历史计时。

|---|---:|---:|---:|---:|---:|---:|
| 指定新机会：原始本机接收→socket 发送 | 160 | 16.250 | 25.243 | 25.993 | 26.361 | 0/160 |
| 所有实际发单，包含背景订单依据报价年龄 | 265 | 16.490 | 39.991 | 61.072 | 73.940 | 11/265 |

接收 10,799,990 条，入队/处理均为 1,687,878 条；行情队列峰值 482、结束为 0。
过载丢弃、溢出、过期拒绝、漏发指定新机会、重复 CID 均为零；完整性通过，10ms 验收未通过，退出码 2。
结束时仍有 66 个按 1.5 秒节奏等待的撤单请求，属于撤单积压，不能称为“所有队列均已清空”。
这些请求没有再耗尽新单配额。完整保存快照最终约 304KB，包含压力期间积累的意图、待撤身份和审计数据；
标记 JSON 的文件大小不代表真实快照大小。

指定新机会分段 P95：排队 6.548ms、出队→选中 5.968ms、选中→登记 0.129ms、
登记→保存完成 14.137ms、保存回执→worker 1.700ms、续发准备 0.254ms。
