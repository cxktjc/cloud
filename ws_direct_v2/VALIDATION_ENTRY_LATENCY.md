# 首次下单时间与后台 I/O 延迟（2026-11-20）

## 用户问题与结论边界

用户观察到 39 秒的行情到 41 秒才挂单成功。旧版本未保留完整的该笔接收/发送/响应时间，
无法据此把约 2 秒全部归因于计算。以下改动提供后续订单的实测证据，不回填 THEUSDT 的历史时间。

代码中可确认的等待来源包括：每个 I/O worker 首次用到时才建立自己的交易 WS、
先撤后换的撤单队列及明确保留的回包后 1.5 秒间隔、交易所回包、owner 轮询，以及最多 3 秒一次的面板刷新。
面板显示时刻不能代替实际发送或回包时刻。

## 时间记录

- 入场登记时保存该单依据的行情来源、交易所时间、原始接收单调时间及其 UTC 毫秒映射。
  行情 UTC 与单调时钟在锁外配对转换，避免把锁等待重复减入接收时刻。
- `decision`：已选定此单、开始登记流程前。接收至该点包含排队与选择。
- `registered`：精确身份/占位落盘返回之后；不代表请求已发出。
- `worker`：工作线程开始执行该次单笔/批量任务。
- `send`：单笔 WS 在连接/锁等待、最终保护检查和签名之后，紧贴 `socket.send` 调用前记录。
  REST_BATCH 在调用现有 HTTP 批量请求原语前记录，包含其后的签名/HTTP 建连/请求过程；通道单独标注。
- `response`：WS 收到匹配请求 ID 的响应；REST_BATCH 请求原语成功返回。
  这是响应返回，不自动表示订单接受，更不表示成交。
- `owner_ack`：owner 取出回包并验证精确提交 ACK 成功之后。

`首次下单` 是本次 trade 启动后、同一 signal session / 币对 / 入场 bar 中最早的实际发送尝试，
有明确 position_id 时进一步核对。未发出的本地拒单不抢占“首次”，重挂/补挂不会覆盖早先已发送的记录。
匹配使用计划索引，不为每条明细扫描整个订单历史。耗时由单调时钟计算，系统时间跳变不改变分段耗时。
无采集证据的旧单显示“未记录”，不把信号确认时间、`placed_at_epoch` 或行情交易所时间冒充发送时刻。
这些记录不算成交证据，也不改变原先仅凭精确归属正成交量更新的漏开统计。

显示位置仍为 trade 的 `未成交明细`，每笔追加：

```text
首次下单=<UTC毫秒> 收到行情=<UTC毫秒> 来源=tick/depth 通道=WS/REST_BATCH 行情时间=<UTC毫秒>
该单登记=<UTC毫秒> 回包=<UTC毫秒> 主线程确认=<UTC毫秒>
分段耗时: 收行情→判断=...ms 判断→登记=...ms 登记→线程=...ms 线程→发送=...ms 发送→回包=...ms 回包→主线程确认=...ms
```

反馈与已跟踪订单账本附加同样的诊断字段；worker 只修改独立、带锁的进程内时间记录，
仍不修改账本或仓位。owner 在原有保存节点复制记录，不为计时新增每条行情的日志或磁盘写入。
成功下单日志附 `entry timing`，记录精确 CID、关键毫秒时间及分段耗时。

## 提速改动

- 启动 worker 时预热其原有独立交易连接。worker 数仍受原 1～19 配置约束，默认 19；
  live 模式最多提前打开对应数量的交易 WS，并沿用现有 Ping/Pong/后台恢复。
  预热仅建连/保活，不发送订单；预热失败不遗失队列工作，不自动重放订单。
  面板新增“交易连接启动预热”汇总。
- 没有新完成回包时，不再逐行情扫描任务表；没有精确查询任务时，跳过查询身份集合和队列清理。
  有查询时仅在有效身份或新查询变化后清理。回包处理/落盘异常仍保留完成事件供 owner 重试。
- 完成回包主动向 market 队列投递唤醒，owner 应用结果并立即安排维护，减少静默时至多 250ms 的轮询等待。
  worker 不执行维护、不变更执行状态；满队列时由正在运行的 owner 继续排空/读取完成事件。
- 保留所有准入、精确订单身份、落盘后派发、UNKNOWN 不盲目重发、先撤后换以及 1.5 秒撤单间隔。
  本次没有降低 0.5 秒过期丢弃门槛或扩大队列，也未改变 signal/策略/历史持仓。

空闲后台回包处理的同机微测：8 个挂单、无查询/回包、1 个空闲 worker，连续调用

这是特定函数路径的 CPU 开销，不能等同于端到端下单时间。
