`204.107 - 58.538 = 145.569ms`。约 146ms 是本币报价在这一轮唤醒之前就已存在的时间，
不能全部解释成行情队列等待。该轮真正排队 0.553ms，但唤醒至发送的 **58.538ms 仍未达到 10ms**。
各分段相加约 58.539ms，与 58.538ms 的差异来自三位小数舍入。
本币报价可能有年龄；本次不会以发送时重新读一个新时间戳来缩短显示延迟。

本次将 socket 发送前同步写报价日志移至回包后，并新增以下分段：

- 保存后续发至进入 socket 协程：worker/broker 循环交接。
- socket 协程进入至 socket 就绪：锁等待及连接恢复。
- socket 就绪至检查完成：账户、精确身份、期限、容量和原 1.5% 分级报价检查。
- 检查完成至编码完成：签名、参数处理和 JSON 编码。
- 编码完成至发送标记：本地统计及发送探针交接。

这些分段用于拆开原来的 21.697ms；没有历史探针，不能事后断言这 21.697ms 全部由日志或 socket 锁造成。
保存成功后才发单的约束继续生效；到期 MARKET 平仓、撤单 1.5 秒间隔保持。

## WS 故障与下撤单统计

行情 WS 接收循环与交易请求使用独立连接。用户面板存在 keepalive timeout 和没有 close frame 的连接结束，
也有历史累计 overflow=88、过载丢弃=53,574，而当前丢弃为 0/s、队列为 0。
这些值不能证明断线由频繁下撤单造成，也不能用当前队列为 0 排除过去发生过处理延迟。

新增统计共用一个进程内对象，由各交易 worker 的实际传输路径更新：

- 最近 1/10/60 秒的入场、平仓、撤单、查询请求尝试数。
- 60 秒内单秒请求峰值、当前/启动后峰值在途请求数、请求最多的三个币对。
- 请求失败类型或 API 错误码，明确的 -1003/-1015/429/418 限频计数。
- REST batch 的 HTTP 请求数与成员订单数分别记账；成员拒绝单列。
- socket 发送检查在网络发送前拒绝的次数，独立于网络请求数。
- 行情接收 asyncio 循环每 100ms 一个延迟探针，保留窗口内最大值。
- 每次实际行情连接故障保存当时前 10 秒请求量、请求错误、接收循环延迟、在途请求及行情队列大小。

故障快照附在 `WS 最近报错` 对应行下，并写入完整 trade.log 的 `WS failure context ... prior10s=...`。
同一错误合并时使用最近一次故障的快照，完整日志保存每次快照。
本地 owner 队列 overflow、定时换连接和正常停止不算 socket 故障。
行情故障总数分别统计 tick/depth；该数和请求累计总数都从本次进程启动开始。

窗口用单调时钟的秒桶；正在发生的一秒尚未完整，因此不是精确的滑动毫秒窗口。
统计只覆盖当前 trade 的交易 WS 请求及 REST 入场 batch，不统计别的程序、订阅/心跳控制帧或公网 IP 的全部请求。
请求尝试表示调用发送接口，不证明交易所已收到或成交；传输未知仍由原精确 CID/订单回报查询恢复。
统计不保存签名、密钥或请求 payload；请求数低于行情数，不逐行情记账或写文件。

对比故障前快照可判断是否同时出现请求高峰、限频回包或接收循环延迟。
时间上相关仍不等于确定因果；此版本不自动修改订阅、准入价差或撤单频率。

## MDT 的明确协议拒绝

面板显示 MDT 实际发送 134 次，最近异常为 `Please sign TradFi-Perps agreement contract fapi.`。
之前这个具体拒绝文案不在保守分类中，会保留 UNKNOWN；补挂的明确拒绝又可能在十秒后换 CID 重试。
不能仅凭最近一条异常推断历史 134 次发送的全部原因。

本次把该明确协议拒绝纳入已拒单分类，同一笔 signal position_id 的补挂保存权限拒绝标记，
不会因新报价、十秒到期或 trade 重启而再次提交；signal 持仓结束或更换 position_id 后才恢复新机会。
普通单继续使用原来的“同一计划已拒绝则禁止再发”规则。其他普通报价拒绝仍按 v16 等更新的合格行情重试。
带连接故障的异常链仍保留 UNKNOWN，不据协议字样释放可能已经成交的身份。
不自动擦除旧 UNKNOWN/实际订单；旧身份仍必须通过精确查询或订单流解决。
